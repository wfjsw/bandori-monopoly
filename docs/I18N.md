# Internationalization

No display text lives in the code. The engine, the server and the web client all
pass message **keys**; the web client renders them in the active language. Data
files (`data/*.json`) stay in the game's own language — tile names, card texts
and character names are content, not UI copy.

## Where strings live

| namespace | file | what |
|---|---|---|
| `game` | `webui/src/i18n/locales/<lang>/game.json` | protocol messages: match log, prompts, command errors, room errors |
| `ui` | `webui/src/i18n/locales/<lang>/ui.json` | web client copy |
| `cards` | `rules/*/locales/<lang>.json` -> `dist/cards/locales/` -> `webui/public/assets/i18n/cards-<lang>.json` | card-module strings |

Locales ship zh-CN (source language of the game data) and English; both files
carry the same key set. `tools/i18n/check.py` fails the build when code and
locales drift apart (a missing key would render as a raw key, a stale one is
dead weight).

## The wire format

The Rust side has no locale files at all. `crates/game-core/src/msg.rs` defines
the message the engine, server and wasm glue send instead of text:

```json
{ "k": "log.roll", "a": { "who": { "player_id": 2 }, "n": { "i": 6 } } }
```

Arguments are typed so the client can resolve them against the match data:
`player_id` -> player name, `tile` -> tile name, `card` / `event` / `char` / `band` ->
data names, `n` -> money with thousands separators, `i` -> plain integer,
`msg` -> a nested message (optional clauses render as empty), `list` -> joined
with the locale's separator (`、` / `, `). Compose sentences from parts where
word order differs per language (`log.part.*`), rather than string-concatenating
in Rust.

`webui/src/i18n/msg.ts` (`fmtMsg`) turns one into display text; `core/names.ts`
supplies the lookups. Card modules send the same JSON (`card-sdk::msg::Msg`)
with namespaced keys, `key!("placed")` -> `cards:card-hhw-hagumi-marks.placed`.

Keys are flat (`log.roll` is one key, not nested): i18next runs with
`keySeparator: false`, matching the Rust keys and the card crates' locale files
exactly.

## Writing UI copy

```tsx
import { t as tr } from "../i18n/t";   // `tr` avoids colliding with locals named t

<h3>{tr("deckPick.heading", { char: c.display })}</h3>
```

The key names the string (`deckPick.heading` = "Pick a deck for {{char}}"), the
value lives in both `ui.json` files. Rules that bit during this port:

* **no module-level `tr()`** — a constant computed at import freezes the old
  language. Use a function: `const steps = () => [tr("board.stepStart"), ...]`.
* **modal bodies** are rebuilt every render (`cloneElement` in `ui/Modal.tsx`),
  so components inside re-translate; a language switch also reopens the settings
  popup so its own title follows.
* switch languages with `setLang()` from `i18n`; it bumps a version the shell
  re-keys its tree on (`useLangVersion`), so every mounted string re-reads.
* display punctuation belongs to the locale too: `common.paren`, `common.quotes`,
  `common.noteColon`, `game:list` cover `（）`, `「」`, `：`, `、`.

## Commands

```sh
python tools/i18n/scan.py      # lines that still carry CJK in code (should only be data keys)
python tools/i18n/check.py     # code <-> locale drift (missing / stale keys)
node tools/build-ruleset.mjs    # card modules + their locale bundles
```

Remaining Chinese in code is intentional and data-shaped: `GENERAL_BAND`
("通用" from `cards.json`), card tag keys in `ui/Card.tsx` (`"手"`, `"反击"`, ...),
character/card ids in Rust tests, and language endonyms in `i18n/index.ts`.
